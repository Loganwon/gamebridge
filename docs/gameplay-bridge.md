# GameBridge：跨游戏内容与玩法桥接

日期：2026-10-27（Asia/Shanghai）。状态：需求修正与架构设计；运行时和游戏适配器尚未实现。

## 用户目标与当前差距

用户希望把游戏 A 的角色、道具、动作和玩法带进游戏 B，形成新的可玩体验；以 Minecraft 的史蒂夫和玩法进入艾尔登法环为参照，希望工具能通过扩展覆盖更多游戏。该例子不等于指定首发组合。

现有 v0.1 只处理静态建筑的几何和颜色，没有完成这个目标。它可作为资产辅助模块保留；继续增加地图格式、把网站改名或生成规则 JSON，都不能作为玩法互联的交付。

## 参照项目：核查到什么

本次只阅读公开文档与协议资料，没有安装、运行或实机验证外部项目。下列功能陈述来自项目作者；不代表 GameBridge 已实现。

- [Minecraft Ring 作者帖子](https://www.reddit.com/r/EldenRingMods/comments/1wwzmzv/i_made_minecraft_playable_inside_elden_ring/)解释：Minecraft Java 和艾尔登法环同时运行，分别保留自己的系统，通过桥交换移动、攻击与交互，再合成画面。这为保留 A 的复杂玩法提供了另一条路径，不必先把全部规则重写进 B。
- [Windows 项目 README](https://github.com/siddoff/Minecraft-Ring)列出建造、战斗、原生交互和画面合成，并明确是实验项目，限定离线单人及特定游戏版本。能放置 Minecraft 方块不代表能挖掘法环原生地形；多人和其他版本尚未验证。
- [第三方来源声明](https://github.com/siddoff/Minecraft-Ring/blob/main/THIRD_PARTY_NOTICES.md)将其描述为 justbustin 项目中法环桥的 Windows 移植。[上游 README](https://github.com/justbustin/minecraft-crossover-bridge)说明自己的实现受 Tobyn Jacobs 的想法启发，已经分别处理法环与怪物猎人：世界。不能将这些独立实现与原视频所用程序认定为同一个版本。
- [上游架构说明](https://github.com/justbustin/minecraft-crossover-bridge/blob/main/docs/how-it-works.md)把画面、相机、地形、敌人和伤害分开同步，并单列移植新游戏的工作。来源一侧可复用部分较多，目标一侧仍有专门适配；坐标单位和死亡规则也有差异。
- [Windows 开发说明](https://github.com/siddoff/Minecraft-Ring/blob/main/docs/development.md)区分状态交换和帧传输，记录碰撞、平台、切换与回归测试；这些工程细节说明“两个游戏合在一起”还需要处理时序、状态归属和恢复。

案例通过原生 DLL 和游戏内部挂钩接入；作者声明反作弊运行时桥不会激活。这不是官方允许的证明，也不提供在线安全保证。当前 GameBridge 约定不实现进程注入、内存修改或反作弊规避，因此这里只借鉴职责划分与协议思路，不能据此把法环列为已支持目标或直接照搬该接入方式。

## 产品应当怎样使用

以下是设计目标，尚不是现有网页能力：

1. 选择 A、B 的具体版本和运行平台；分别识别来源端与宿主端的可用适配器。
2. 选择带入的内容，例如角色操控、武器战斗、建造、背包；展示每项依赖和交互限制。
3. 明确运行方式：两款游戏同时运行，或在 B 中安装重新实现的玩法包。需要运行 A 时直接说明。
4. 本地启动受支持的会话，检测两端准备状态，再接通控制和交互；显示真正的连接状态。
5. 在真实游戏中游玩，停止会话时归还控制。存档按明确的世界映射保存，支持恢复与卸载。

GitHub Pages 可以承担说明、配置与兼容性展示。运行中的游戏需要本地程序与对应插件承接；现有静态网页没有这类访问能力。

## 主线架构（设计）

```text
游戏 A：角色、物品及玩法运行
             ↕ 来源适配器
GameBridge 本地会话与统一协议
             ↕ 宿主适配器
游戏 B：世界、敌人、交互及进度

可选：画面合成 / 原生资源与动作转换 / 静态场景工具
```

| 层 | 应负责的工作 | 不能由该层自动保证的事情 |
| --- | --- | --- |
| 来源适配器 | 暴露 A 的角色、动作、物品、事件及必要的画面数据 | 读取任意封闭游戏的全部逻辑 |
| 会话与协议 | 身份和版本协商、能力检查、时间与坐标映射、消息流量限制、断线恢复 | 提供目标游戏不存在的编辑能力 |
| 玩法映射 | 实体对应、伤害换算、交互转发、控制归属与死亡规则 | 两个玩法系统天然兼容或自动平衡 |
| 宿主适配器 | 经获允许的接口操作 B 的相机、场景、实体和交互 | 同引擎的所有成品游戏共享相同接口 |
| 渲染适配 | 在接口允许时组合角色、画面、深度和 UI，或使用 B 的原生资源 | 单纯叠加窗口就能正确遮挡和交互 |
| 本地管理工具 | 启停、诊断、版本锁定、会话存档、恢复与卸载 | 网站发布即等于安装了游戏插件 |

这套拆分是 GameBridge 的设计判断。适配器可以复用，但兼容性仍要逐条组合验证。新增游戏不应要求重写整个框架，也不能只加一个名称就宣称支持。

## 协议首先要约定的语义

- **能力与版本**：声明可读、可控制的功能；所需能力缺失时阻止启动该玩法。区分研究中、模拟通过、适配器实现、实机通过四种状态。
- **空间与世界**：坐标轴、单位、区域 ID、稳定原点和角色尺寸；传送或换图后使旧区域的碰撞与实体消息失效。
- **状态归属**：每个字段只有一个最终决定方。例如 B 决定敌人生命和任务进度，A 决定其背包；伤害是请求，最终结果由归属方返回，避免双方同时扣血。
- **时序与去重**：会话 ID、序号、时间戳、实体代次与事件 ID；处理重复攻击、延迟回复、暂停和加载界面。画面需绑定对应相机状态，不能用任意一帧相机合成。
- **交互一致性**：分别说明 A 能否碰撞 B 地形、B 敌人能否踩上 A 建造物、双方武器能否互伤。显示相同画面不代表共享同一物理世界。
- **生命周期**：控制权切换、死亡/复活、重连、保存与恢复；一端失联后停止发送操作，不能无限重放未确认事件。
- **资源限制**：消息大小、实体/查询数量、队列长度、每帧工作预算；畸形消息拒绝执行。实现时为这些约束提供测试。

事件/条件/动作规则可承担伤害或任务映射，但不能替代角色控制器、碰撞、动画和渲染。

## 原生玩法包路线（次级设计）

如果 B 提供足够的脚本或 Mod 接口，也可以在 B 内重建选定玩法，仅运行 B。此时需明确哪些模型、动作、物品可导入，哪些逻辑必须重新实现；资源转换、骨骼动作适配与玩法逻辑是独立工作。不会承诺从任意游戏自动提取并无损迁移整套玩法。

## 第一条可玩链路的验收

先确定一组可获允许接入、可实际运行的 A/B 与版本，限定一项有意义的玩法；Minecraft × 法环目前只是研究案例。首个闭环应包含：

1. A 的角色或玩法在 B 的真实场景中由玩家操作，移动和碰撞位置一致。
2. A 的一次攻击/操作影响 B 的真实实体；确认反馈、反击或消耗回到 A，重复消息不造成重复结算。
3. 死亡/复活或该玩法对应的失败恢复正常；打开菜单、暂停、切换控制和换图不会留下旧状态。
4. 保存、退出、重启后恢复所声明的状态；中断连接后可恢复原生操作。
5. 记录游戏/插件/系统版本、帧率和延迟、已知限制及实机结果。生成文件、单元测试或浏览器模拟不得替代上述记录。

验证这一条链路后，再接入第二个宿主，检验协议与来源适配器能否复用。首发游戏组合和本机测试环境仍需明确；目前没有已接通的游戏会话。
