# GameBridge 完整设计方案

版本：Design 0.2 · 2026-10-28（Asia/Shanghai）。状态：设计基线，尚无游戏桥接实现或实机兼容结论。

本方案替代原静态建筑转换方向。旧转换器代码、网页工作台、样例、格式文档与对应测试已从当前版本删除，Git 历史保留。本文描述后续要开发的产品；展示页可以阅读方案，不具备游戏连接能力。

## 1. 产品定义与成功标准

**GameBridge 是一个跨游戏内容与玩法组合工具：让玩家选择游戏 A 中的角色、操作、道具和玩法，在游戏 B 的世界中体验，并让双方产生真实的交互结果。**

以用户举的体验为例，玩家希望史蒂夫带着自身操作和武器进入另一个游戏，使用武器击败那个游戏的敌人、被敌人反击，也能按已支持的规则建造。Minecraft × 艾尔登法环用于研究这一类体验，不限定项目只能支持 Minecraft，也不代表用户已选定首发组合。

验收关注三件事：

1. **能玩**：A 的操作和玩法对 B 的真实世界产生作用，B 的结果能够反馈回来。
2. **能扩展**：接入第二个宿主时能复用会话、协议及来源适配器，而不是重新写一套独立程序。
3. **能管理**：安装、版本检查、启动、停止、存档恢复和插件更新有明确流程，出错时可退出并恢复控制。

“支持游戏”必须具体到来源版本、宿主版本、方向、玩法、平台和限制。例如 A→B 通过战斗验收，不推出 B→A、建造玩法或新版本也可用。

## 2. 用户、使用场景与内容单位

第一阶段服务愿意在本机单人环境测试的玩家，以及具备对应游戏 Mod 开发经验的适配器作者。普通玩家需要选组合、选玩法并启动；作者需要明确接口和测试工具，能把新游戏接进已有框架。

产品围绕“体验配方”组织内容。配方描述一段可玩的组合及其依赖，不打包完整商业游戏：

| 内容 | 玩家希望得到的体验 | 转化时必须处理 |
| --- | --- | --- |
| 角色与动作 | 在 B 中使用 A 的角色形象、移动和操作 | 控制器、相机、体型、动作状态、碰撞、输入归属 |
| 武器与战斗 | A 的近战/射击/能力对 B 敌人有效 | 命中对象、伤害规则、反馈、冷却、投射物、敌人反击 |
| 物品与背包 | 使用 A 的道具，消耗和获得有明确意义 | 物品命名空间、所有权、数量、掉落规则、持久化 |
| 建造与破坏 | 在 B 的空间里放置 A 的构造并与之交互 | 放置规则、碰撞、持久化；B 的 AI 是否识别需另验收 |
| 成长与任务 | 将部分奖励或成长映射到新体验 | 进度归属、奖励去重、条件冲突；不默认融合两个主线存档 |

一个配方包含所选 A/B、各端版本、启用模块、能力要求、数值映射、状态归属、安装清单和验收证据。分享配方不分享用户存档、凭据或未经许可的游戏素材。

## 3. 已研究案例与推论

本轮阅读了一手项目文档，没有运行或验证这些外部项目。

- [Minecraft Ring](https://github.com/siddoff/Minecraft-Ring)描述两款游戏同时运行：Minecraft 负责玩家、背包与建造，法环负责世界和敌人，中间交换交互并组合画面。作者把它标为实验性、限定版本的离线单人项目。
- [上游项目](https://github.com/justbustin/minecraft-crossover-bridge)已有面向法环和怪物猎人：世界的专门实现；[移植说明](https://github.com/justbustin/minecraft-crossover-bridge/blob/main/docs/how-it-works.md#porting-it-to-another-game)明确新宿主仍需处理相机、碰撞、实体、伤害与渲染。不能因为复用了来源端，就视为任意游戏可接入。
- [来源声明](https://github.com/siddoff/Minecraft-Ring/blob/main/THIRD_PARTY_NOTICES.md)说明 Windows 项目与上游的关系；它们不应与最初传播视频所用的具体构建混同。

**设计推论**：优先保留 A 的玩法运行环境，通过适配器把 B 的世界信息和交互接入；把通用协议、生命周期和配方工具抽出来。单纯写一个“事件→动作”规则编辑器，无法承担角色控制、碰撞和画面融合。

**接入约束**：参考项目使用原生 DLL 和游戏内部挂钩，这与本项目不实现注入、内存修改或反作弊规避的约定不同。我们借鉴其分工与同步问题，不直接采用其接入方式。法环在本项目仍是研究案例；没有获允许且足够的接口，就不能被列为可启动目标。离线单人也不自动等于官方允许或零封禁。

## 4. 技术路线决策

| 路线 | 实现方式 | 优点 | 成本与条件 | 本项目安排 |
| --- | --- | --- | --- | --- |
| 双运行时桥接 | A、B 同时运行，各自保留系统，插件交换必要状态和画面 | 能复用 A 已有的复杂玩法 | 双游戏资源开销；双方接口、时序和渲染条件要求高 | 主研究及首个可玩切片路线，先验证接入条件 |
| 原生玩法包 | 在 B 的 Mod/脚本系统内重建选定的 A 玩法与获许可内容 | 玩家运行 B 即可，宿主整合更自然 | 需要重写逻辑、动作适配和资源转换，难自动无损 | 后续独立路线，单独标注支持与验收 |
| 轻量事件联动 | 两个游戏交换成就、奖励或状态 | 接入面较小 | 不提供角色与空间融合体验 | 可作为底层测试，不计作核心产品完成 |

主路线不可行时，不偷偷降级成事件联动并标记成功。应展示缺少的能力，停止该配方；另行说明是否存在原生玩法包的设计路径。

## 5. 玩家使用流程

**选择组合 → 选择内容 → 检查兼容性 → 准备本地插件 → 启动 → 游玩 → 保存与退出。**

玩家首先选择自己的游戏安装及精确版本。GameBridge 按“游戏版本＋插件版本＋玩法方向”匹配兼容记录；无记录显示待验证，不推测兼容。随后选择已具备依赖的玩法模块，预览带入内容、B 保留的系统、已知损失和资源要求。

启动前只对受支持目录和接口执行必要准备，列明所安装文件及备份。启动完成以两端握手和游戏就绪回执为准；进程存在不等于已连接。游玩时提供少量状态和退出入口，详细调试面板仅给作者使用。停止时先停止新交互、结清已确认结果，再归还控制并记录会话状态。

页面、按钮、错误文案、恢复分支详见 [产品流程与实机验收](product-and-validation.md)。

## 6. 系统架构与职责

```text
                  GameBridge 桌面管理器
          游戏选择 / 配方 / 兼容报告 / 启停 / 诊断
                           │ 控制面
                  GameBridge 本地会话服务
           能力协商 / 映射 / 状态机 / 事件记录 / 恢复
                 ↙                         ↘
         A 来源适配器                  B 宿主适配器
       角色、动作、物品                 场景、敌人、进度
                 ↖  状态、查询与交互结果  ↗

    高速画面与空间数据通道：由获支持的两端接口直接交换
    远端网站：方案、兼容资料和版本索引，不在游玩数据路径中
```

| 模块 | 输入与输出 | 边界 |
| --- | --- | --- |
| 桌面管理器 | 用户选择 → 校验后的配方与会话操作；回显真实状态 | 不承担每帧物理和图像传输 |
| 本地会话服务 | 插件握手、消息 → 经过验证和映射的请求/结果 | 不读取任意游戏进程内存；只使用适配器公开能力 |
| 来源适配器 | A 的角色、物品、动作、画面 → 标准化状态；接收反馈 | A 的系统不是天然可序列化，按具体功能声明 |
| 宿主适配器 | B 的空间、实体、交互 → 查询结果；执行允许的请求 | 在游戏指定线程或回调执行，不能跨线程任意调用 |
| 配方与映射 | 能力需求、单位、实体对应、数值规则 → 运行配置 | 只有数据与受限规则；不从配方执行任意脚本 |
| 渲染与碰撞通道 | 帧、深度、相机、空间查询 → 对齐后的显示和交互 | 需要宿主接口支持；叠加窗口不等于正确空间融合 |
| 本地存档与恢复 | 会话日志、各游戏存档引用 → 可核查恢复点 | 不承诺两个独立游戏存档可原子提交 |
| 适配器 SDK 与验收工具 | 接口定义、录制样本、回放与探针 → 合约和实机记录 | 模拟通过必须和实机通过分开 |

“通用”指可复用这些模块和协议。A/B 两个单独适配器通过测试后，组合仍需一份配方级验证记录；能力齐全也不保证组合玩法平衡。

## 7. 游戏接入与兼容策略

接入先回答三个问题：是否有可用且获允许的接口；接口是否足够表达目标玩法；是否能够在具体设备和游戏版本上实测。

官方 Mod 接口也有功能边界。[Luanti 官方文档](https://docs.luanti.org/for-creators/creating-mods/)提供 Lua 游戏/Mod API，[Factorio 官方运行时文档](https://lua-api.factorio.com/latest/index-runtime.html)提供事件和世界对象操作；这些仅证明有公开接口，不证明它们可实现本方案的全部相机、跨进程渲染或玩法组合，也不把这两款产品设为首发。

适配器清单需要记录：游戏身份、构建版本、来源/宿主角色、平台、接口出处、允许的使用模式、能力、权限、依赖、资源预算、已知缺陷、测试证据。未知版本先阻止启动。禁止用“使用同一引擎”推断两个成品游戏兼容。

组合级状态统一为：**研究中 → 接口探针通过 → 合约验证通过 → 实机验证通过 → 发布可用**；失败、过期和上游更新导致的失效单独标记。当前所有游戏组合均未达到实机验证通过。

## 8. 关键交互设计

| 难点 | 设计决定 |
| --- | --- |
| 同一角色谁控制 | 每项状态只有一个最终决定方。首个切片拟由 A 控制玩家、B 决定敌人和世界结果；具体配方显式声明 |
| 攻击如何结算 | 来源发送命中意图，宿主校验实体/距离/规则后结算并回传结果；单次事件有 ID，重复请求不能重复扣血 |
| 不同游戏尺度 | 坐标变换含单位、轴向、手性、区域原点；角色大小、相机与碰撞一起验证，不能仅改显示比例 |
| 敌人如何识别 A | 使用宿主允许创建/控制的代理实体或明确受支持的角色映射；没有这种能力则战斗模块不可用 |
| 放置物是否真实 | A 可以站上构造不代表 B 的敌人也能；渲染、碰撞、导航、可破坏性四项分别声明 |
| 画面是否同步 | 同一帧的颜色、深度和相机状态关联；旧帧和新相机不得随意混用。缺少深度能力时不能标记完整融合 |
| 载入与死亡 | 进入明确的暂停/载入/恢复状态，淘汰旧区域事件；复活规则和背包保留策略由配方确定 |
| 异常与存档 | 结果不明时暂停并对账，不盲目重发伤害或奖励；不能安全恢复时从已知恢复点重新开始 |

具体字段、消息和时序见 [运行时与适配器协议](runtime-protocol.md)。

## 9. 内容与玩法转化工具链

工具接受三类输入：经过登记的玩法适配模块、用户获准导出的内容，以及在目标游戏接口内重新实现的玩法定义。不能通过选择一个游戏目录就承诺自动理解全部代码、提取全部资源或复制整个玩法系统。

拟定转换流程为 **盘点内容 → 判断来源与许可 → 分析目标能力 → 生成映射建议 → 显示损失/冲突 → 构建目标包或桥接配方 → 验证 → 安装**。所有步骤给出可审阅产物。角色资源需处理骨骼、动作、碰撞和材质；动作状态必须与攻击窗口及移动同步；物品需独立命名空间并定义消耗、堆叠、掉落和保存。

双运行时模式优先让 A 继续执行自身玩法，减少整套逻辑转换。原生玩法包模式才需要把机制重建成 B 的脚本或组件，两条路线不能混用验收结果。商业原始素材和游戏可执行文件不进入公开仓库或配方包。

AI 可以辅助读官方文档、生成适配器草稿、提出字段映射和测试用例；开发者审查并通过测试后才纳入版本。游玩实时路径不依赖大模型；不运行用户自然语言直接生成的任意代码，不把 AI 推测标成已支持能力。

## 10. 技术选型与平台范围

以下为拟定选型，本轮仅交付设计，没有安装或实现这些组件：

| 部分 | 拟定方案 | 决策理由与验证点 |
| --- | --- | --- |
| 管理界面 | Tauri 2＋TypeScript | 桌面系统能力与 Web UI 分离；必须限制命令与目录权限 |
| 会话核心 | Rust 独立进程 | 处理有界队列、协议校验、状态与日志；崩溃不应自动连带退出游戏 |
| 游戏适配器 | 遵循各游戏支持语言/API，必要时提供窄 C ABI | 不强迫所有插件用同一种语言；各自按指定运行线程执行 |
| 协议 | 版本化接口定义；控制消息先用严格 JSON；高速状态按测量结果选有界二进制通道 | 不把全帧图像编码进 JSON，不让 UI 转发每帧数据 |
| 传输 | 本机命名管道/Unix socket；游戏接口只允许本地 HTTP 时单独评估鉴权与权限 | 按平台和接口选择，不假定所有 Mod 具有任意 IPC 能力 |
| 帧交换 | 支持时使用游戏公开接口提供的 GPU 资源共享；受控 CPU 方案作性能验证 | 缺少合法接入能力就阻止该渲染路线；格式和同步需平台实测 |
| 存储 | 会话清单、版本锁、恢复点和有界事件日志 | 初期不建云服务；需要时引入本地数据库并记录迁移方案 |
| 网站与协作 | 现有静态 GitHub Pages、GitHub Actions | 展示方案与版本资料；不控制本地游戏，不上传游戏数据 |

[Tauri 官方 IPC 说明](https://v2.tauri.app/concept/inter-process-communication/)与[安全模型](https://v2.tauri.app/security/)支持桌面界面/核心的职责划分，但不提供游戏兼容性。此桌面选型需在首个接口探针后确认；如果宿主仅支持另一种部署环境，以可玩接入为先。

首发只承诺一个经过验证的操作系统、一个 A/B 方向和一个完整互动切片。Windows x64 是原生 PC 游戏研究的候选；当前开发机器为 macOS 不代表已完成 Windows 或 CrossOver 支持。具体平台随首发组合一起确定，多平台同步首发不进入 MVP。

## 11. MVP、后续范围与交付物

MVP 选择“角色控制＋一种武器＋真实敌人双向战斗”作为建议切片；最终应依据首发游戏能开放的接口确定。它要覆盖移动碰撞、命中、反击、死亡恢复、暂停切换与重新载入。建造、完整背包、技能树、跨游戏任务、多人、移动平台与复杂交通系统后续分别加入，不用功能数量取代完整闭环。

MVP 交付应包含：一个可安装的本地管理器、一组来源/宿主适配器、一份可用配方、安装及恢复说明、锁定的版本清单、自动测试、实机录像/日志和兼容报告。SDK 的抽象先保持最小，在第二个宿主验证复用后稳定，避免先设计大量无人实现的接口。

本轮的交付不同于 MVP：完整设计文档、设计展示页、旧设计清理，以及可持续更新的仓库；没有游戏二进制插件。

## 12. 开发阶段、人员与预算方法

| 阶段 | 工作与产物 | 进入下一阶段的条件 |
| --- | --- | --- |
| M0 接入可行性 | 明确 A/B、版本、平台；查证接口和使用模式；在游戏内做控制/碰撞/伤害/显示探针 | 有获允许且可实际操作的接口，能证明核心闭环所需能力；否则停止该组合 |
| M1 最小互联 | 来源端、宿主端、本地会话服务；最小消息与状态归属 | 一个真实场景内完成移动、命中、反击和恢复；模拟器仅用于辅助测试 |
| M2 可玩 Alpha | 加入菜单切换、载入、退出恢复、存档边界与错误处理 | 按产品文档完成重复实机验证，无未解释的重复结算或数据损坏 |
| M3 工具化 | 配方、安装卸载、兼容检测、日志导出、版本锁和更新回滚 | 新测试者按文档可安装、游玩、停止并恢复；发布每条验收记录 |
| M4 扩展证明 | 同一来源接第二宿主，或第二来源接同一宿主，增加一种内容能力 | 证明核心可复用，记录专用代码和必须新增的语义，才扩大适配目录 |

规划估算而非承诺：M0 可按 1–2 人周做限时探针；接口齐全后，M1–M3 合计初始预算约 8–16 人周，覆盖核心、游戏插件、界面与测试。游戏 API、渲染或动画存在缺口时可能显著超出，不能用此估算承诺首发日期。M0 未通过不进入长期开发。

建议角色为核心/协议负责人、熟悉首发游戏的适配器开发者、桌面工具开发与实机测试负责人，小团队可兼任。开发者、测试设备、游戏版本及可用接口是排期输入；不预设当前已具备这些条件。M4 重新按新游戏探针估算。

## 13. 验收、性能与证据

完整验收分为协议单测、适配器合约测试、异常回放及真实游戏会话。任何自动测试数量都不能替代最后一项。建议记录 30 分钟连续会话、重复启停、切换/死亡/载入/中断恢复以及同一事件重发；具体次数和门槛见产品文档。

性能基线必须在同一设备、画质与场景测四组：A 单独运行、B 单独运行、A/B 同时运行但未桥接、A/B 桥接。区分双游戏本身开销和桥接增量；记录 p50/p95/p99 帧时间、输入到可见反馈延迟、CPU/GPU/内存和队列积压。不得承诺所有设备稳定 60 FPS。每条数字目标均为待验证预算，实测不达标就调整配方或不发布。

发布记录包含源代码提交、游戏/插件版本、设备、场景、步骤、结果、失败和已知限制。上游游戏更新后兼容性降为待复验；不能自动把旧记录复制给新版本。

## 14. 本地数据、插件与更新

按最小权限访问已选游戏目录和会话目录，令牌留在系统安全存储或会话内存，不进入 Git。插件包固定版本和内容哈希，列出来源和文件清单；签名证明发布者身份，不能代替审查。未经验证的插件不得通过“配方文件”自动下载并执行。

游戏存档保留原所属游戏；桥接记录世界映射、扩展数据和可恢复点。版本升级先检查停机状态、备份和迁移路径，完成后验证；失败时回退插件并使用相容的恢复点，不能用旧代码强读已迁移的新存档。用户正在游玩时不自动替换插件。

GitHub `main` 推送继续自动更新文档网站。未来桌面程序和插件采用独立的发布流程，只有带实机证据的组合进入可用目录。初期不做云账号、市场付费、遥测上传或自动收集用户游戏素材。

## 15. 风险与停止条件

| 风险 | 应对及停止条件 |
| --- | --- |
| 没有获允许的必要接口 | M0 列出缺口，不以注入或反作弊规避补齐；该组合暂停 |
| 两套物理/控制互相纠正 | 固定状态归属；移动/碰撞不能稳定即不继续加内容 |
| 画面能合成但交互是假的 | 必须在真实敌人/物体上验证结果；纯视觉演示不标可玩 |
| 受击重复、掉落复制或崩溃后结果不明 | 事件去重、结果对账和恢复点；无法判断时停止会话，不自动重放 |
| 游戏更新破坏插件 | 精确版本锁、失配阻止启动、回归后重新发布兼容记录 |
| 资源开销过高 | 先测双游戏基线；达不到体验预算则降低已声明能力或停止发布该配方 |
| 内容权利或规则不明确 | 只使用自有/获许可资产和可查证接入方式；未确认内容不随包分发 |
| 需求不断扩展 | 每次只增加一个可验收的玩法模块或一条组合；未通过 M2 不建设插件市场 |

## 16. 待决事项与下一步输入

完整方案不等于替用户选定第一组游戏。实施前仍需确定：第一组 A/B 与最想移植的玩法；具体游戏版本和可用测试设备；是否接受两款游戏同时运行带来的资源成本；可使用的 Mod/API 及素材范围。

这些事项不妨碍本轮完成设计，但决定 M0 的探针和后续排期。只有 M0 用真实接口证明可行后，才把具体组合写入开发承诺。第一步实现应是该组合的核心互动闭环，随后再把验证过的公共部分沉淀成通用工具。
