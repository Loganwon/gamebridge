# GameBridge 产品、交付与验收设计

> 本文记录旧玩法执行层的验收思路；自动化 AI 制作流程及当前实现状态以 [AI Mod 工作台](ai-mod-workbench.md) 为准。不能把本文件的未来实机阶段当作已完成结果。

版本：Design 0.2。日期：2026-10-28（Asia/Shanghai）。本文描述拟实现产品，不代表已有游戏适配器或实机结果。整体架构见 [完整方案](gameplay-bridge.md)，消息与运行时约定见 [运行时协议设计](runtime-protocol.md)。

## 1. 产品目标与成功标准

GameBridge 帮助玩家把游戏 A 的角色、道具、动作和玩法带进游戏 B：玩家在 B 的世界里使用 A 的内容，操作能影响 B 的真实对象，B 的结果也能反馈给 A。转换的结果应是一段可玩的体验。

产品的复用价值是把接入、映射、配置、启动、保存和验证做成统一工具链。一个游戏仍需对应的适配器，具体组合仍需兼容配置和实机验收。增加游戏名称或导出 JSON 不算增加支持。

首个成功标准是完成一个有游戏乐趣的互动闭环；第二个成功标准是把已经验证的来源端接到第二个宿主时，能复用核心协议和相当部分工具链。第二阶段以实际变更记录衡量复用程度，不预先承诺复用百分比。

静态建筑转换器不属于本设计的交付，不作为辅助功能继续保留。Minecraft × 艾尔登法环仅作为研究参照，首发游戏组合尚未选择。

## 2. 用户与主要场景

| 用户 | 主要任务 | 产品应交付的结果 |
| --- | --- | --- |
| 想尝试跨游戏体验的玩家 | 选择已验证组合，配置少量玩法选项，开始和结束游玩 | 清晰的兼容范围、可重复启动的会话、可靠的保存与恢复 |
| 制作体验的玩家或作者 | 组合支持的内容模块，调整数值与规则，分享配置 | 不含游戏素材和账号数据的体验配方，以及确切依赖 |
| 游戏适配器开发者 | 接入一款游戏的获允许接口，声明能力并验证 | SDK、合约测试、调试工具和可复现的验收报告 |
| 项目维护者 | 审核适配器、发布版本、定位回归 | 能追溯版本与证据的兼容清单、发布门槛和回滚方案 |

典型体验包括“用 A 的角色控制和武器挑战 B 的敌人”“在 B 的环境中使用 A 的建造系统”“将 A 的道具机制带入 B 的探索”。这些是产品方向示例，不代表已经支持某款游戏。

## 3. 运行方式与首发范围

### 3.1 两种运行方式

| 方式 | 玩家运行什么 | 实现责任 | 阶段 |
| --- | --- | --- | --- |
| 运行时桥接 | A、B 和本地 GameBridge 同时运行 | A 保留选定玩法；适配器与桥接层让它与 B 的真实世界交互 | 首发主路线 |
| 原生玩法包 | B 加载适配后的内容和玩法包 | 把选定资源和规则重新实现为 B 支持的内容；逐项记录特征损失 | 后续路线，不与首发同时铺开 |

配置界面必须说明是否需要同时运行 A。两种方式不得使用同一个笼统的“转换成功”状态；分别报告“会话已接通”或“玩法包已生成并通过对应验收”。

### 3.2 建议的首个纵向切片

在尚未确定具体游戏时，首发切片定义为：**一种 A 角色的操控方式、一种攻击或工具操作，在 B 的一个可重复测试区域中作用于真实对象，并正确获得反馈**。

若候选组合适合战斗，优先采用“移动、碰撞、近战命中、敌人反击、死亡与复活”的闭环；若游戏没有战斗，则用同等复杂度的资源消耗、目标变化和失败恢复替代。验收内容必须在选定组合后冻结，不能遇到困难就退化为只显示模型。

首发仅覆盖一组精确版本、一个可验证的操作系统/图形环境、单机及获允许的 Mod 或插件运行方式。具体游戏与系统由接入调查和可用测试环境共同决定，不能仅凭引擎名称决定。

### 3.3 内容范围按阶段展开

| 内容 | 第一条可玩链路 | 复用与扩展阶段 | 暂不承诺 |
| --- | --- | --- | --- |
| 角色与操控 | 一个角色、必要视角、移动和操作反馈；视觉与碰撞对齐 | 多个角色配置、尺寸和输入方案 | 任意角色自动完整迁移 |
| 动作与动画 | 所选操作需要的可见动作和命中时机 | 原生玩法包的骨骼映射、动作替换及逐项校正 | 自动保留所有动作、布料和表情 |
| 战斗/工具 | 一类操作、双向结果、消耗或冷却、失败恢复 | 远程攻击、状态效果、多类武器与平衡配置 | 所有武器、Boss、技能系统无损通用 |
| 建造与破坏 | 不进入首发必需范围，除非首选体验以此为核心 | 另建能力包，分别验证双方碰撞、放置和持久化 | 看到建筑就认为 B 的敌人能站上去；任意挖掘 B 地形 |
| 背包与物品 | 只保留首发操作必需的来源物品和数量；不跨库复制 | 明确物品映射、消耗、丢弃及两端恢复 | 自动合并两套完整经济与背包 |
| NPC 与任务 | B 保持原生任务、对话和进度，提供必要控制切换 | 在接口允许时映射有限事件与交互 | 通用移植所有 NPC AI、剧情和任务 |
| 世界与存档 | 一个测试区域，保存会话关联，加载后重新校验 | 多区域、传送、移动平台、跨会话内容 | 两款游戏共用一个可无条件回滚的存档 |
| 多人 | 不进入首发 | 仅在独立需求、服务器许可和同步设计通过后研究 | 在线竞技兼容、零封禁 |

## 4. 从选择游戏到结束游玩的完整流程

### 4.1 本地游戏库

玩家选择 A、B 的已安装位置或应用支持的启动入口。首发不扫描整台电脑，不上传本地路径。管理器检测游戏版本、操作系统和适配器所需的运行环境，并显示“已识别”“版本未知”或“需要手动指定”。

无法识别的版本不能套用近似版本继续运行。已知但没有适配器的游戏可以加入本地愿望清单，页面应显示“尚无适配器”，不显示可点击的开始按钮。

### 4.2 选择来源、宿主与运行方式

界面以“A 提供什么”“B 保留什么”展示方向。例如同一游戏能作为来源，不代表其宿主侧可接入。玩家切换 A/B 时重新计算兼容性，不沿用原组合的通过状态。

运行方式由所选配方与能力决定。运行时桥接需要展示双游戏资源需求；原生玩法包需要列明哪些内容来自重新实现。不存在可行方式时展示缺失能力及当前证据，不自动转成静态素材导出。

### 4.3 选择内容与体验配方

玩家选择角色操控、武器/工具等已支持模块。依赖自动展示，例如“远程攻击需要投射物与宿主命中反馈”；不兼容组合立即标记原因。基础界面只显示对体验有影响的设置，如角色比例、伤害倍率、按键和死亡规则。

每份配方保存来源/宿主方向、精确版本、适配器版本、能力模块、规则参数和存档关联。共享配方剥离绝对路径、账号、存档、凭据和不可再分发素材。配方是会话配置，不能被描述为迁移后的整款游戏。

### 4.4 兼容报告与准备

开始前展示本次运行的实际状态：支持的功能、缺失的功能、已知限制、精确版本匹配、所需插件及保存策略。结果分为“可以开始”“需要完成准备”“当前组合不可用”。

“可以开始”仅在接口依据、版本匹配、必需能力、安装完整性与会话恢复条件均满足时出现。未知目标、未知版本、未获允许的接入方式或缺少关键碰撞/交互能力均阻断启动；不提供“忽略所有限制”的通用开关。

### 4.5 启动与接通

桌面管理器按适配器声明的顺序启动或连接已运行的两端，验证它们进入可交互状态，建立本地会话，再交接控制权。加载界面、游戏菜单与可玩世界分别显示；只有完成双端握手且必要能力可用才显示“已接通”。

失败时指出是哪一端、哪个准备步骤出现问题，并提供重试、查看本地日志或退出。退出准备阶段必须撤销尚未完成的控制接管；不能把“A 已启动”显示成两款游戏已串联。

### 4.6 游玩与控制切换

玩家使用选定玩法参与 B 的世界。必要提示在桌面会话页展示；仅当游戏接口支持时，才提供游戏内提示。不得为展示状态额外加入未获允许的游戏内覆盖层。

显式快捷键或管理器按钮切回 B 的原生操作，用于菜单、对话或未映射交互。切换期间暂停桥接动作、清理按键保持状态并确认接管完成。断线、暂停和加载均有可见状态，不能继续显示“正常游玩”。

### 4.7 保存、结束与恢复

正常结束先停止新动作，处理已确认结果，记录会话检查点，调用支持的保存接口，再归还控制并释放资源。A、B 各自仍管理原生存档；管理器记录两端检查点与对应关系。

异常退出后先检查两端存档与会话记录是否一致。无法确定是否已发生的攻击、消耗等操作不得自动重放。无法对齐的会话显示可恢复选项与可能丢失的进度，禁止声称跨两个独立存档可做到无条件原子回滚。

卸载仅撤销安装清单记录的项目文件与配置；保留用户存档和自有内容。若文件已被其他工具改动，显示冲突并允许用户选择保留，不能覆盖用户修改。

## 5. 信息架构与页面状态

| 页面 | 玩家要完成的事 | 核心状态与错误处理 |
| --- | --- | --- |
| 首页 / 游戏库 | 查看可用组合与最近会话 | 空库、版本未识别、游戏未安装、适配器不可用分别展示 |
| 新建体验 | 选择来源 A、宿主 B 和方向 | 无适配器、方向不支持、版本不匹配时给出具体原因 |
| 内容与规则 | 选择已支持模块，调整体验参数 | 参数越界、依赖冲突、功能降级需逐项说明 |
| 兼容报告 | 判断当前组合是否具备开始条件 | 已验证、待准备、不可用；证据日期和限制可展开 |
| 启动与会话 | 接通、切换控制、保存、结束 | 准备中、等待游戏进入世界、已接通、暂停、失联、恢复中、已结束 |
| 存档与恢复 | 查看会话关联并恢复可恢复状态 | 正常检查点、两端不一致、备份缺失、恢复冲突 |
| 插件与版本 | 安装已审核适配器、锁定或回滚版本 | 更新可用、签名/完整性失败、宿主版本不符、回滚不可用 |
| 开发者诊断 | 在本地定位失败环节和生成报告 | 默认隐藏账号、路径、存档内容；导出前预览报告 |

面向玩家的界面使用“谁提供角色、带入哪些玩法、当前能否开始”等语言。协议字段、内存帧格式和事件队列只进入开发者诊断，不占用主要操作路径。

## 6. 桌面程序与网页边界

| 交付面 | 职责 | 不具备的职责 |
| --- | --- | --- |
| 项目网页 | 说明产品、发布设计、展示带证据的兼容清单和版本说明，提供下载入口 | 直接连接未安装适配器的游戏；伪装本机运行状态 |
| 本地桌面管理器 | 本地识别、配方编辑、插件管理、会话控制、诊断、存档关联 | 自动解除游戏保护、自动绕过接口限制 |
| 游戏端适配器 | 使用获允许的接口向游戏传递操作或读取必要状态 | 将未支持游戏版本当成兼容版本 |
| 开发工具 | 合约测试、可重复事件回放、诊断与实机记录 | 以模拟器通过替代真实游戏验收 |

首发不需要云账号、远程控制、社区市场、自动下载游戏资产或云存档服务。静态网页更新与桌面程序/插件升级是不同发布通道；GitHub Pages 发布成功不等于玩家游戏适配器已经升级。

## 7. 兼容性怎样证明

兼容记录的最小单位是“来源版本＋宿主版本＋方向＋操作系统/图形环境＋两端适配器版本＋玩法模块集合”，不使用笼统的“支持某引擎所有游戏”。

每条记录至少包含接口来源与允许使用的依据、取得日期、版本标识、必需能力、双向交互范围、验证设备与配置、用例结果、已知问题、复现材料和维护者。游戏升级、插件升级或关键配置变化后，旧记录不自动扩展到新版本。

| 状态 | 必须存在的证据 | 产品呈现 |
| --- | --- | --- |
| 研究中 | 可追溯的接口/案例资料与未解问题 | 不可开始，显示研究范围 |
| 接口探针通过 | 在目标版本加载并确认核心接口可调用的记录 | 开发验证状态，不代表完整玩法可用 |
| 合约验证通过 | 适配器能力、消息与故障测试结果，区分模拟和实际端点 | 仅开发验证，不展示发布支持 |
| 实机验证通过 | P01–P11、P14 及对应组合的设备、版本、实机结果 | 可玩 Alpha，仅覆盖声明范围，尚需分发验证 |
| 发布可用 | P01–P14 全部通过，安装、升级、回滚及使用文档完整 | 可按文档部署的已验证组合 |
| 回归待复验 / 已撤回 | 上游版本变化或可复现故障 | 阻止新会话或锁定已验证版本，提供原因 |

“通过验收”描述工程证据，不是封禁风险等级。获允许的接口与运行模式是接入前提；离线运行本身不能证明所有平台或游戏规则都允许，也不能据此承诺零封禁。

## 8. MVP 功能清单与验收

以下为设计验收，不是测试已通过的记录。每项必须记录结果；不适用项必须说明原因，不能在失败后改为不适用。

| ID | 必需能力 | 验收方法 | 通过条件 |
| --- | --- | --- | --- |
| P01 | 版本和方向识别 | 正确版本、未知版本、交换 A/B 分别测试 | 仅声明支持的方向/版本进入准备流程 |
| P02 | 能力与依赖检查 | 去掉一个必需能力，加入一个冲突模块 | 明确阻断相应配方，不静默缩减核心体验 |
| P03 | 真实双端连接 | 两端进入世界、停在菜单、缺少一端分别启动 | 状态与真实准备程度一致，无虚假接通 |
| P04 | 角色与空间一致 | 在固定区域行走、转向、跳跃或对应动作，经过台阶和边界 | 视觉、操作与碰撞在冻结的误差预算内，无法通行处正确阻挡 |
| P05 | 操作影响宿主 | 用 A 的选定攻击/工具作用于 B 的真实对象 | B 正确变化，并能继续触发 B 原生反应或交互 |
| P06 | 双向结果 | 接受 B 的反击、失败或消耗反馈 | A 正确响应，双方不重复结算、不同时争夺最终状态 |
| P07 | 控制权切换 | 反复进入菜单、切回 B、再恢复 A | 没有按键粘连、双重操作和隐藏的持续动作 |
| P08 | 失败和复活 | 触发所选玩法的死亡/失败并恢复 | 恢复点、资源归属和实体对应与配方一致 |
| P09 | 暂停、加载和换区 | 暂停、加载或配方支持的区域切换 | 旧区域操作失效，未准备好时不接管，不误操作新实体 |
| P10 | 保存与重开 | 正常结束后重新启动两端 | 声明可持久化的状态恢复，原生存档可正常使用 |
| P11 | 异常中断 | 分别中断 A、B、管理器并重连 | 停止新动作；不重放结果不明的副作用；提供可解释的恢复路径 |
| P12 | 安装与卸载 | 在干净安装与有用户改动的环境安装、卸载 | 可撤销项目自有修改，不删除用户内容或覆盖冲突文件 |
| P13 | 升级与回滚 | 升级适配器后用旧配方启动、回滚至已验证版本 | 版本约束生效，不自动迁移无法回退的存档 |
| P14 | 持续游玩 | 按同一路径重复游玩并记录异常与资源曲线 | 完成冻结的测试时长，无持续资源增长和影响基本游玩的错误 |

M2 可玩 Alpha 必须通过 P01–P11、P14，允许在开发环境按受控步骤准备插件。M3 工具化后还须通过 P12、P13，并重跑受影响用例，P01–P14 全部通过才标记发布可用。建造、远程攻击、移动平台、原生动作移植等扩展能力分别增加专门用例，不凭基础用例结果推断通过。

## 9. 性能与体验如何测量

先记录 A 单独运行、B 单独运行、两端同时运行但未桥接、桥接开启四种基线。保持设备、电源模式、分辨率、图形设置、测试场景与路线一致，预热后至少重复三轮。使用公开允许的游戏/系统测量接口；不得为了采样引入项目禁止的接入方式。

测量内容包括总帧时间的中位数与 P95/P99、低帧表现、游戏线程额外开销、输入到目标反馈的延迟、状态陈旧时间、消息丢弃与队列峰值、CPU/GPU/内存、暂停/换区/控制切换的耗时。整体双游戏成本与桥本身的增量成本分开报告；没有共同时间基准时说明测量误差。

首轮建议使用连续 30 分钟游玩、20 次控制切换、10 次失败恢复或重连作为**拟定测试样本量**，不是充分证明稳定性的标准；正式发布前扩大设备、场景和持续时长。协议预算由 [运行时设计](runtime-protocol.md)给出，实机阈值在首组 A/B 和参考设备确定后冻结。

不提前宣称“固定 60 FPS”或“零延迟”。如果最低参考配置无法获得可接受的交互延迟或稳定帧时间，应缩减可选模块、降低画面传输成本或更换接入路线；核心交互仍不成立时停止该适配器，而不是用视频或浏览器模拟替代。

## 10. 本地数据、内容来源与发布

游戏目录、玩法状态和存档默认本地处理；体验配方与诊断报告只在用户主动导出时离开设备。日志默认隐藏账号、凭据、绝对路径和用户内容，保留定位故障所需的版本、错误类型与计数。

公开仓库放项目自己的代码、设计、可再分发测试夹具与明确许可的依赖。用户拥有游戏副本不自动代表其资产可以重新分发；模型、动作、音频和脚本应记录来源、许可及使用方式，无法确认时不随插件包或示例发布。具体授权问题按来源条款核验，不在界面提供笼统“版权安全”标签。

适配器的开源协议与游戏素材权限分别登记。若未来复用外部代码，先核查许可证、第三方声明和实际复用范围，再保留必要署名；“参考架构”不等于已经复用了某个仓库。

桌面管理器和适配器在会话结束后提示可用更新，不在游玩途中自动替换组件。发布物包含版本、完整性校验、兼容记录、变更说明和回滚条件。GitHub 自动化可执行合约测试和构建，真实游戏验收仍需对应环境与人工/受支持测试流程。

## 11. 里程碑与停止条件

| 阶段 | 交付物 | 进入下一阶段的条件 | 不满足时的处理 |
| --- | --- | --- | --- |

| M1 最小互联 | 两个真实游戏适配器的最小能力、诊断工具、协议合约测试 | 在一个真实场景完成移动、命中、反击与恢复，不依赖模拟端冒充 | 修正接口或缩小配方，核心能力缺失则停止 |
| M2 可玩 Alpha | 选定角色/操作、双向反馈、控制切换、恢复与保存 | P01–P11、P14 通过，性能与局限有记录 | 修复阻断问题，不标记实机验证通过 |
| M3 工具化 | 安装、配方、兼容报告、启动、会话与卸载完整流程 | P01–P14 全部通过，新测试者能按说明完成体验，无开发终端手工修补 | 保持开发预览状态，补齐可用性与恢复 |
| M4 扩展证明 | 复用来源接第二宿主或复用宿主接第二来源，并建立独立组合档案 | 核心不因单一游戏被整体重写，两条链路分别通过验收 | 调整协议边界，明确仍需组合专用规则 |

M4 后按独立能力包扩展建造、远程攻击或原生玩法包；每项都要有真实用例、版本依据和特征损失说明，未通过则维持不支持状态。

M0 完成前不提供固定交付日期或承诺接入数量。其余工作量受接口开放程度、版本稳定性、画面与碰撞能力、测试硬件及团队配置影响；排期应在 M0 后按实际证据估算，并将适配、工具链和实机验证分别列出。

## 12. 主要风险与设计响应

| 风险 | 具体表现 | 设计响应与退出条件 |
| --- | --- | --- |
| 接口不足 | 只能显示内容，无法影响宿主对象或正确碰撞 | M0 先核实必要能力，核心闭环缺失则不选为首发 |
| 双运行时成本 | 两端竞争 CPU/GPU，合成使延迟过高 | 分项测量与有限能力包；参考设备上仍不可玩则暂停该路线 |
| 游戏版本变化 | 原接口或行为变化，旧存档/配方不再对应 | 精确锁定版本、能力重新协商、回归待复验状态 |
| 双方状态冲突 | 重复伤害、重复消耗、死亡点不一致 | 单一状态归属、确认结果、事件去重与不明结果停机恢复 |
| 物理语义不一致 | A 能站在 B 地面，但 B 敌人穿过 A 建造物 | 分方向公布碰撞能力，限制配方并单独验收 |
| 内容迁移复杂度 | 动作、骨骼、特效或脚本无法直接兼容 | 原生玩法包逐项转换与重建，不给出无损承诺 |
| 接入规则不明 | 技术可运行但允许使用范围未知 | 记录依据与范围；未知状态不纳入可开始列表 |
| 存档不可原子保存 | 一端写入成功，另一端崩溃 | 检查点关联、恢复前核对、明确可能丢失的进度 |
| 插件质量与供应链 | 插件版本混用、包被替换、共享配方含敏感数据 | 审核发布、校验完整性、锁定依赖、导出最小化 |

## 13. 实施前需要确定的事项

以下信息影响适配实现与排期，不影响本设计的整体成立：

1. 首选 A/B 和最想保留的玩法；优先选择能够验证双向互动的组合。
2. 可使用的系统、图形环境、两款游戏版本和测试硬件，是否具备相应的本地运行条件。
3. 接口允许使用的具体范围，以及哪些游戏资产可以本地使用或重新分发。
4. 第一条切片的失败/死亡、物品消耗、存档归属和可接受的功能损失。
5. 参考设备上的帧时间、延迟与稳定性门槛；这些目标应在开发切片前冻结，避免事后修改标准。

完成上述调查后产出一份具体组合档案，再实施适配器。当前交付是完整设计基线，不能被描述为已经生成跨游戏插件或已经完成游戏融合。
