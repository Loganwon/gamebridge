# GameBridge 运行时与适配器协议设计

设计版本：Design 0.2 · 2026-10-28（Asia/Shanghai）

本文是拟实现的工程规格，没有对应的运行时、SDK 或已认证游戏插件。文中的接口名、数值预算和示例 ID 都是设计约定；`example.*` 表示虚构测试端，不表示已支持任何游戏。产品范围与开发顺序见 [完整设计方案](gameplay-bridge.md)。

## 1. 设计依据与实现边界

公开的 [minecraft-crossover-bridge 架构说明](https://github.com/justbustin/minecraft-crossover-bridge/blob/main/docs/how-it-works.md)把相机、碰撞、实体、伤害与画面分别交换，并说明不同宿主需要各自适配。[Minecraft Ring 开发说明](https://github.com/siddoff/Minecraft-Ring/blob/main/docs/development.md)进一步记录状态/帧分离、切换控制和地形失效处理。这些是一手项目文档所描述的做法，我们没有实机验证。

下面是 GameBridge 自己的设计，不复用这些项目的内部地址、挂钩或加载方案。游戏接入只使用官方或明确获允许的 Mod、插件、脚本接口；没有满足条件的接口时，组合状态为不支持。系统不提供进程注入、内存修改、反作弊规避或“零封禁”保证。

主路线是两款游戏同时运行，保留来源玩法，再由适配器连接宿主世界。另一路线是在宿主内重新实现选定玩法，仅运行宿主；两者在会话配置中显式区分，不能把角色换皮或规则文件导出标成完整玩法迁移。

## 2. 组成与职责

```text
桌面工作台 ── 本地会话控制器 ── 版本/组合/能力检查
                    │
      来源适配器 A ←─┼─→ 宿主适配器 B
                    │
          状态快照 / 请求与结果 / 生命周期
                    │
          可选的帧传输与渲染适配器
```

| 组件 | 负责 | 不负责 |
| --- | --- | --- |
| 来源适配器 | 把 A 的玩家控制、玩法事件、必要实体及画面映射到协议 | 自动解析任意游戏代码 |
| 宿主适配器 | 经允许的接口查询 B 的世界并执行获授权操作，返回权威结果 | 猜测未知版本的接口或数据布局 |
| 本地会话控制器 | 身份、兼容性、消息路由、控制租约、记录与故障恢复 | 在两个物理引擎之间制造原子事务 |
| 组合配置 `Pair Profile` | 确定来源/宿主方向、玩法依赖、状态归属、数值换算和验收条件 | 通过配置补出游戏缺失的能力 |
| 渲染适配器 | 使用已协商方式显示角色、世界和 UI | 仅凭透明窗口就保证遮挡、碰撞一致 |

适配器的游戏侧代码随其官方插件机制加载。控制器通过插件主动建立的本地通道通信，不向任意游戏进程注入代码。游戏 API 调用必须由适配器调度到该 API 允许的线程；通信线程只验证并投递有界任务。

### SDK 边界（语言无关契约）

| 接口 | 输入 → 输出 | 约束 |
| --- | --- | --- |
| `probe()` | 无 → 游戏构建、运行模式、可访问 API 和诊断 | 只读，不初始化玩法、不接管输入 |
| `describe()` | 无 → 已验证的清单与本次可用能力 | 静态清单与本次可用能力不一致时取较低能力 |
| `prepareSession(config)` | 锁定配置 → 准备结果、会话句柄、初始世界代次 | 不产生攻击、消费或存档迁移等副作用 |
| `readSnapshot(cursor)` | 上次游标 → 全量或增量权威状态 | 标明基线版本；缺失基线时要求全量快照 |
| `enqueueRequest(request)` | 已验证请求 → 接收/拒绝 | 接收只代表进入队列，不代表游戏已执行 |
| `drainResults(cursor)` | 结果游标 → 请求结果与状态失效事件 | 终态结果可重取，接收方确认游标后才回收窗口内记录 |
| `setControlLease(lease)` | 已协商租约 → 接受/拒绝 | 只在 READY/ACTIVE 的合法交接中使用，支持立即释放 |
| `captureCheckpoint()` | 当前世界绑定 → 完成凭据/不支持/失败 | 仅在具备能力且会话停止新副作用时调用 |
| `closeSession(reason)` | 退出原因 → 资源/控制释放报告 | 幂等；部分失败明确返回，不能谎报已恢复 |

来源端还需发布被选玩法事件；宿主端还需执行已声明的世界操作。它们都通过类型化能力接口暴露，禁止提供 `executeCode`、`readMemory` 或任意控制台命令这类通用逃生口。渲染通道另有 `acquireFrame` / `releaseFrame` 成对契约，必须在断连和停止时回收资源；首版不做跨语言内存结构的隐式 ABI 共享。

## 3. 插件清单与方向性

每个适配器包包含：清单、实现、接口依据链接、权限说明、资源预算、兼容版本、许可与第三方声明、测试报告。公开分发只包含获许可的代码与自有样例；游戏资产、安装目录、存档和账号凭据留在本地。

一个适配器可以支持 `source`、`host` 或二者，但每个角色的能力分别声明。A→B 与 B→A 是不同组合；同一引擎上的两款游戏也不是同一个适配器。

下例是清单格式草案，不能直接用于安装或建立连接：

```json
{
  "manifestVersion": 1,
  "adapterId": "example.host-adapter",
  "adapterVersion": "0.1.0",
  "protocol": { "major": 1, "minor": 0 },
  "game": {
    "id": "example.host-game",
    "builds": ["test-build-001"],
    "platforms": ["windows-x64"]
  },
  "roles": ["host"],
  "integration": {
    "kind": "permitted-mod-api",
    "evidence": "https://example.invalid/replace-with-verified-api-source"
  },
  "capabilities": {
    "entity.observe": "1.0",
    "combat.requestDamage": "1.0",
    "combat.observePlayerHit": "1.0",
    "collision.queryStatic": "1.0",
    "control.handoff": "1.0",
    "render.nativeAvatar": "1.0"
  },
  "permissions": ["game.api", "ipc.session", "storage.adapter-private"],
  "budgets": {
    "maxControlMessageBytes": 65536,
    "maxTrackedEntities": 256,
    "maxQueuedRequests": 256
  },
  "validation": { "status": "design-only", "report": null }
}
```

`builds` 使用可验证的游戏构建标识；正式支持项不能写 `latest` 或任意版本。`integration.evidence` 在审核时必须替换为真实依据，示例无效地址必须阻止认证发布。清单中的“通过”不能由插件自证：官方兼容目录还需引用与包摘要、游戏构建、组合配置匹配的独立验收记录。

协议大版本不同直接拒绝。小版本通过显式能力交集协商；未知必需字段、必需能力及其不兼容版本拒绝启动，未知可选扩展只忽略该扩展。每种消息使用封闭字段集合，扩展放入带命名空间的 `extensions` 中；不得把任意键名或字符串当作代码执行。

## 4. 组合配置与协商结果

组合配置独立于插件包升级，采用精确版本与摘要锁定。其最小内容为：

| 字段 | 含义 |
| --- | --- |
| `profileId` / `profileVersion` | 稳定 ID 与配置版本 |
| `mode` | `dual-runtime` 或 `native-gameplay-pack` |
| `source` / `host` | 游戏构建、平台、适配器版本与包摘要 |
| `features` | 选择的角色、战斗、建造等内容；每项注明必需/可选 |
| `requires` | 每项玩法需要的两端能力及版本 |
| `authority` | 玩家、相机、敌人、生命、背包、进度的最终决定方 |
| `mapping` | 坐标、单位、伤害/消耗换算、实体和资源标识映射 |
| `worldBinding` | 来源桥接存档与宿主存档/区域的对应关系 |
| `limits` / `fallback` | 双方预算的较低值，以及允许的降级策略 |
| `evidence` | 合约测试和真实游戏验收报告的关联 |

启动顺序是：验证包与依据 → 检查游戏版本和模式 → 两端握手 → 求能力交集 → 校验玩法依赖 → 形成不可变会话配置摘要 → 两端确认准备完成 → 交接控制。任一必需能力缺失时保持未连接，并给出具体缺口。

可选能力降级只能发生在启动前，用户能看到“不会保留什么”。运行中失去必需能力必须暂停桥接或归还原生控制，不得静默继续。需要修改玩法、数值或版本时创建新会话，首版不做战斗中的热更新。

例如“来源近战进入宿主世界”至少需要来源命中事件、宿主实体观察/受击处理、反向受击反馈、控制切换和一种经过验证的角色呈现方式；仅能读取宿主 HP 的插件不能满足该玩法。

## 5. 状态所有权

每项可变状态必须只有一个权威方。下表是拟定的首条战斗链路默认模板，最终由具体组合审定：

| 状态 | 默认权威方 | 其他端的行为 |
| --- | --- | --- |
| 来源角色移动意图、动作状态 | A | B 接收经过约束的位置/动作表达，不再次计算同一输入 |
| 宿主地形、敌人、NPC、任务进度 | B | A 使用带版本的代理/快照，不独立推进任务 |
| 宿主敌人生命值 | B | A 发出伤害请求，按返回结果更新代理表现 |
| 来源背包与来源道具耐久 | A | B 引用映射后的道具 ID，不直接改 A 存档 |
| 来源玩家生命值 | A | B 的受击作为请求进入 A；B 是否需要原生代理角色取决于允许接口 |
| 相机和输入控制权 | 本地控制器授予单端租约 | 同一时刻只允许一个被授权控制方 |
| 存档实际落盘 | 各游戏自身 | 控制器记录关联与检查点，不伪造跨游戏原子保存 |

“B 敌人生命属于 B”不意味着把 A 的 `damage=10` 原样送给 B。组合配置须规定单位、倍率、上限和伤害类型；B 仍决定抗性、无敌状态、命中有效性和奖励归属。原游戏无法区分合成反馈与原生受击时，必须另设计防回环机制并验证，否则禁用双向伤害。

死亡与复活采用一次 `lifeEpoch` 变更：生命权威方发布死亡结果，组合指定的一端负责复活地点和生命周期，再生成新代次。旧代次伤害不进入新生命。默认不复制任务奖励、货币或跨游戏交易；这些持久经济操作需要更强的幂等接口才可加入。

## 6. 坐标、时间与实体身份

统一空间采用米、Y 向上、右手坐标；位置为有限的 float64，旋转为已归一化四元数 `[x,y,z,w]`。适配器显式提供单位比例、轴转换和原点，不接受凭视觉调准但缺少可重放参数的映射。碰撞尺寸、速度、重力与动画位移使用同一映射；法线按方向变换，不带平移。

每条空间数据带 `worldId`、`regionId` 和 `worldEpoch`。传送、换图或浮动原点变更先关闭旧区域操作，再发布新映射和全量快照；旧代次的查询结果与攻击直接作废。不同世界的同一局部坐标不能共享方块或实体缓存。

实体键为 `{owner, worldEpoch, entityId, generation}`；`entityId` 是稳定的不透明字符串，绝不使用内存地址。实体被删除后仍保留短期墓碑；ID 复用必须增加 `generation`。代理只在匹配快照有效期内参与交互。

每个端使用本机单调时钟与递增 tick，握手通过往返采样估计偏移和不确定度。协议的 64 位序号和微秒时间戳在 JSON 中使用十进制字符串，避免 JavaScript 整数精度损失。UTC 时间只用于诊断显示，不能排序战斗事件。两端不要求逐帧锁步；位置用最新有效快照，离散事件采用请求/结果，视觉可以插值但不得擅自插值出新的命中。

帧图像必须携带其采样时的 `cameraPoseId`、世界代次和色彩/深度约定；宿主不能用另一时刻的相机投影合成。帧过期时丢弃，不让画面等待阻塞游戏线程。

## 7. 消息类别和数据通道

首版控制通道采用本机带长度前缀的 UTF-8 JSON 消息，便于诊断和跨语言实现。实时大批量状态可在性能验证后引入版本化二进制快照；像素和 GPU 资源从第一天就与控制消息分离，不把整帧编码进 JSON。

| 类别 | 语义 | 满载或超时时 |
| --- | --- | --- |
| `hello` / `ready` / `heartbeat` | 协商与存活；独立的优先队列 | 无法确认两端健康则退出活动态 |
| `snapshot` | 当前权威状态，可替代更旧快照 | 丢旧留新，不等待所有历史位置 |
| `request` / `result` | 有副作用操作与权威结果 | 明确拒绝或进入待核对，不静默丢成功结果 |
| `world.changed` / `entity.removed` | 使旧状态失效的屏障 | 先失效缓存，再接受新世界操作 |
| `frame.ready` / `frame.release` | 图像缓冲句柄及生命周期 | 丢弃过期帧并释放句柄 |
| `checkpoint` / `stop` | 受控保存与终止 | 返回实际完成状态和未完成项 |

消息头至少包含 `protocolMajor`、`sessionId`、`sessionEpoch`、`sender`、`sequence`、`sentAtUs`、`kind`。会话配置摘要在握手确认，重连后必须重新确认；不接受未绑定到该会话的发件方。请求还必须有 `requestId`、`requestSequence`、`worldEpoch`、`target` 和带语义版本的请求体。`requestSequence` 是每个发送端在会话内独立递增的副作用请求计数；重传保留原值，不能靠换 ID 把同一个操作变成新请求。

## 8. 一次攻击如何结算

下面两个 JSON 对象是示意性消息，ID 和数值均为测试占位。真正的接口还需按选定游戏生成 schema 与合约测试。

```json
{
  "protocolMajor": 1,
  "sessionId": "example-session",
  "sessionEpoch": "1",
  "sender": "source",
  "sequence": "42",
  "sentAtUs": "8000000",
  "kind": "request",
  "requestId": "example-session:source:7",
  "requestSequence": "7",
  "worldEpoch": "3",
  "target": { "owner": "host", "entityId": "enemy-12", "generation": "2" },
  "payload": {
    "type": "combat.damage.v1",
    "originEventId": "source-hit-7",
    "sourceLifeEpoch": "1",
    "amount": 10,
    "damageType": "physical",
    "mappingRevision": "combat-v1"
  }
}
```

```json
{
  "protocolMajor": 1,
  "sessionId": "example-session",
  "sessionEpoch": "1",
  "sender": "host",
  "sequence": "108",
  "sentAtUs": "8010000",
  "kind": "result",
  "requestId": "example-session:source:7",
  "requestSequence": "7",
  "worldEpoch": "3",
  "target": { "owner": "host", "entityId": "enemy-12", "generation": "2" },
  "payload": {
    "type": "combat.damage.result.v1",
    "status": "applied",
    "appliedAmount": 6,
    "healthAfter": 94,
    "entityRevision": "19"
  }
}
```

流程：A 把原生命中转成请求 → 控制器校验额度与会话 → B 校验世界、目标代次和数值映射 → B 在允许线程通过游戏 API 执行 → B 返回实际结果 → A 更新代理表现。A 可以先播放挥剑动画，但不能提前认定敌人死亡或发奖励。收到重复结果也不能重复扣血。

结果状态限定为 `applied`、`rejected`、`pending`、`indeterminate`。拒绝附错误码，例如 `STALE_WORLD`、`ENTITY_GONE`、`UNSUPPORTED_DAMAGE_TYPE`、`RATE_LIMITED`；不得把超时直接写成已拒绝或已成功。反馈事件携带 `originEventId`，避免合成受击再次变成新的反向攻击。

### 去重与崩溃边界

同一存活会话中，B 以 `requestId + sessionEpoch` 串行化操作，执行前先登记 `pending` 并保留终态结果；重复请求只返回原结果。尚在执行的请求返回 `pending`，不再次调用游戏 API；游戏 API 抛错但无法确认副作用是否发生时也进入 `indeterminate`，不自动重试。队列满时在执行前拒绝新请求，不通过挤掉旧结果来腾空间。

如果游戏 API 本身不支持幂等键、查询事务状态或原子保存，“执行已发生，但结果/账本尚未保存就崩溃”的窗口无法被桥消除。因此不承诺跨崩溃 exactly-once：

1. 控制器与适配器均记录请求和结果，但记录不能被当作游戏实际落盘的证明。
2. 崩溃后所有未确认操作标为 `indeterminate`，禁止自动重放伤害、奖励、物品转移等副作用。
3. 新会话读取权威全量状态，用于重新建立视图；单凭当前 HP 不能反推出某一次请求是否执行。
4. 需要精确恢复的玩法必须由游戏提供幂等或事务检查点接口；缺失时限制到非持久测试场景，或拒绝该玩法配置。
5. 去重账本只覆盖协商的保留窗口。窗口过期后不再接受旧请求，而不是把它当新请求；切换新会话后旧会话事件一律拒绝。

## 9. 碰撞与呈现能力

这些能力彼此独立，不用一个“兼容百分比”掩盖差异。

| 能力 | 达成后可以承诺 | 未达成时的限制 |
| --- | --- | --- |
| `collision.queryStatic` | 来源角色可按宿主静态表面求碰撞 | 只显示角色无法作为可行走桥接验收 |
| `collision.observeDynamic` | 门、可破坏物等变化能使缓存失效 | 不能声称动态地形可用 |
| `collision.trackSupport` | 角色跟随移动平台并正确脱离 | 平台场景列为不支持 |
| `collision.installSourceShapes` | 宿主实体能感知来源建造物的碰撞 | 只能承诺来源端自己使用建造物，宿主敌人可能穿过 |
| `entity.proxyInteraction` | 双方可识别代理实体并映射交互结果 | 只能显示，不能宣称真实战斗 |
| `render.nativeAvatar` | 宿主原生显示获许可的角色与动作资源 | 动作、骨骼和材质仍需具体转换验收 |
| `render.colorDepthComposite` | 相机匹配、深度遮挡和 UI 分层有实机验证 | 缺少接口则不可选择该呈现路线 |
| `render.visualOverlay` | 提供诊断或概念验证画面 | 不满足依赖正确遮挡的可玩组合 |

地形查询结果带区域代次、查询 ID、采样版本与有效期。未采样区域不得默认为可通行；采用配置约定的停止前进、回退或恢复原生控制策略。不能将未知碰撞固定当“空气”，也不能无限扩大采样导致游戏主线程卡死。

建造操作需要额外明确四件事：方块由哪端保存、哪端负责碰撞、宿主 AI 是否能导航、拆除时如何失效。首个战斗闭环不默认包含跨引擎建造物理或导航。

## 10. 会话状态机与控制租约

```text
启动：IDLE → PREFLIGHT → CONNECTING → READY → ACTIVE
暂停恢复：ACTIVE → SUSPENDED → RECOVERING → READY
正常停止：READY / ACTIVE / SUSPENDED / RECOVERING → STOPPING → STOPPED
取消启动：PREFLIGHT / CONNECTING → STOPPING → STOPPED
无法恢复：任意非终态 → FAILED（释放控制并清理会话资源）
```

`STOPPED` 和 `FAILED` 均为终态；重试创建新的会话代次，从 `IDLE` 开始。实现状态图须用测试枚举合法转移，禁止界面自行推断连接成功。

| 状态 | 进入条件与动作 |
| --- | --- |
| `PREFLIGHT` | 核验版本、获允许的运行模式、存档关联、插件信任与能力依赖；保持游戏原生控制 |
| `CONNECTING` | 验证本地端点身份，握手、时间同步、建立资源句柄 |
| `READY` | 两端均确认配置、区域和全量快照，尚未接管输入 |
| `ACTIVE` | 两端确认租约后，唯一控制方接收输入；允许玩法请求 |
| `SUSPENDED` | 菜单、加载、能力失效或超时；禁止新副作用；通过已支持接口暂停或归还原生操作 |
| `RECOVERING` | 重新握手、清理过期句柄/事件、读取快照、核对存档与世界；不能直接恢复旧输入 |
| `STOPPING` | 停止新请求、限时排空已知结果、释放控制与渲染资源、记录保存完成情况 |
| `STOPPED` / `FAILED` | 不再发送游戏操作；保留可读诊断和待核对项目 |

输入租约包含持有端、会话代次、递增租约代次和过期时间。交接时先撤销旧持有端，双方确认中立输入，再发新租约；超时停在中立或宿主原生操作，不能同时驱动两个角色。每个适配器本地有独立看门狗：控制器崩溃后也应停止合成输入，释放光标/相机控制。只能恢复曾由自己修改、且当前仍归自己持有的控制状态。

不能暂停的游戏不应被描述为“已冻结”；界面显示真实的原生运行状态，并限制会话恢复条件。玩法依赖双端可暂停而一端不支持时，该组合拒绝启动。

## 11. 保存、重连与升级

控制器只保存组合配置锁、世界绑定、适配器版本、最近检查点引用和操作账本。A 的玩法存档与 B 的世界/任务存档各自由其合法接口管理；同名角色或目录不等于同一个世界。

有双端检查点能力时：停止新操作 → 等待已知请求结束 → 两端创建本地检查点 → 得到各自完成凭据 → 写入关联记录。跨游戏保存仍可能部分失败；任一端失败则标记检查点不完整，禁止把另一端的新检查点与旧存档悄悄拼接。恢复由已验证策略成对选择检查点，不自动覆盖原存档。

无检查点能力时只提供干净退出与人工选择测试存档，明确无法原子恢复；涉及永久物品/货币/剧情迁移的功能保持关闭。重新连接总是创建新的连接代次，读取两端权威快照并清除旧输入、过期帧和不确定请求；不跨会话重放战斗。

升级只在停止态进行。工作台下载到独立暂存目录，核对摘要与受信发布者签名，执行合约测试，再切换版本锁；不热替换游戏中的插件代码。保留上一版本包与兼容检查点引用，数据库/存档格式迁移采用新副本并记录来源。无法回退的游戏存档升级必须在启用前说明，不能用“插件回滚成功”代表存档也已恢复。

签名证明发布者与包完整性，不证明插件无缺陷、游戏兼容或厂商授权。GameBridge 的兼容目录还需人工审核依据和验收记录；未知发布者包不自动执行。支持撤销版本及撤销原因，下次启动在联网获取到撤销记录后阻止该包；离线时显示目录缓存日期。紧急撤销不会在游戏中直接卸载插件，先停止会话。

## 12. 本地权限与资源预算

首版仅同一台机器、同一用户的离线单人会话。控制通道默认用限制当前用户访问的命名管道或 Unix 域套接字；随机会话端点与短期握手凭据通过受限启动通道传递，不进入命令行、日志或 Git。公共网页不直接连接本机控制器，后续若提供浏览器集成须另设计来源验证与显式配对。

控制器不要求管理员权限，不开放任意文件读写、任意命令执行或游戏内存调试接口。原生游戏插件不能因清单限制就被称为已沙箱化，因此只加载经过信任审核的插件，权限仅授予完成该组合所需的范围。日志默认脱敏路径、账号和存档标识；崩溃转储不自动上传。

下表是第一版拟定的保守上限与调优起点，尚无性能实测。每个组合可要求更低值；需要提高时必须补压测和实机依据。

| 项目 | 初始预算/规则 |
| --- | --- |
| 控制消息 | 每条最多 64 KiB，JSON 深度 16；字符串、数组按 schema 另限长度 |
| 实体 | 最多跟踪 256 个近场实体；超限不静默漏掉必需敌人，暂停或明确限制作用区 |
| 副作用请求 | 每方向最多 256 个排队请求；发送速率按玩法另定，禁止无界积压 |
| 快照 | 初始 30 Hz；保留最新快照，不排队补播全部旧帧 |
| 游戏线程工作 | 每帧桥接任务目标不超过 2 ms；超过预算分批或暂停，不忙等 |
| 心跳/失联 | 初始 250 ms 心跳、连续 1 s 无有效回应进入暂停；适配器看门狗独立执行 |
| 请求等待 | 初始 1 s 转入待核对；慢任务需明确 `pending` 与总期限，不能无限延长 |
| 去重窗口 | 最多 4,096 个已完成请求或 60 s，以先到为限；过期 ID 永不作为新请求执行 |
| 帧缓冲 | 最多 3 个在途槽；分辨率、格式和 GPU 预算在启动时协商；不预先承诺 4K |
| 数据验证 | 拒绝 NaN/Infinity、负长度、未知必需枚举、无效实体/世界代次和超额查询 |

去重窗口的“过期 ID 永不执行”依赖 `requestSequence` 和接收端最低可接受水位；删除完整结果时仍保留水位及窗口内孔洞集合。水位只能跨越已终止或明确放弃的序号，不能越过尚在执行的操作；窗口内过大的序号跳跃直接拒绝。保留窗口外的查询可返回 `RESULT_EXPIRED`，发送端不得换 ID 自动补发同一攻击。按字节和数量同时限制队列，避免少量巨型对象绕过数量预算。

图像吞吐必须单独测量。例如未经压缩的 1920×1080 RGBA8 单帧约 8.3 MB，60 帧每秒仅颜色就约 498 MB/s，尚未包括深度和复制；因此不能假设 JSON、普通 socket 或 CPU 回读能承担全部画面传输。优先用平台允许的 GPU 共享接口；不存在可用路径时选择原生角色呈现，或判定该渲染模式不支持。

## 13. 合约测试与实机验收

协议实现先用确定性测试端和故障注入验证；它只证明所测协议满足合约；组合还需真实接口探针与适配器合约证据才能进入“合约验证通过”，不能直接进入“发布可用”。

| 测试 | 必须观察到的结果 |
| --- | --- |
| 错误版本/角色/必需能力 | 保持未连接，错误说明包含具体缺口，不接管输入 |
| 非法长度、深度、数值、枚举 | 拒绝消息，内存与队列不无界增长 |
| 重复攻击/结果、乱序/延迟消息 | 同一存活会话内只结算一次，不能击中新代次实体 |
| 执行前/执行后/回执前崩溃 | 未确认操作标记不确定；恢复不重放副作用 |
| 换图、传送、实体 ID 复用 | 旧碰撞、旧帧、旧命中均失效 |
| 相机帧错配、慢帧、GPU 句柄失效 | 丢弃过期帧且释放资源；游戏线程不被等待卡住 |
| 控制器或任一插件退出 | 本地看门狗回收合成输入与租约，可恢复原生操作 |
| 速率/实体/查询超限 | 按配置拒绝、缩小范围或暂停，不能静默冒充全覆盖 |
| 单边保存失败、升级失败 | 不生成伪完整检查点，旧版本与原存档不被覆盖 |
| 未授权本地客户端、包摘要错误 | 无法获得会话控制；插件不执行 |

实机报告必须绑定游戏 A/B 精确构建、系统、硬件/驱动、适配器/组合版本及摘要。记录真实移动碰撞、攻击与反击、死亡复活、菜单切换、换图、保存重开与恢复的可复现步骤、结果及已知缺口；报告帧时间 p50/p95/p99、桥接延迟和队列峰值。性能阈值由选定游戏与硬件基线制定，不能把双游戏运行成本全部算成桥本身开销。

首条链路完成后，复用来源适配器接第二个宿主，或复用宿主接第二个来源。记录复用的协议/代码与必须新增的游戏逻辑，作为“工具具有通用扩展能力”的证据。公开状态统一按组合方向登记为研究中、接口探针通过、合约验证通过、实机验证通过、发布可用；失效、待复验与撤回另行记录。状态推进需逐项证据，单个合成测试通过不自动使组合升级；网页演示不能替代真实游戏的支持状态。
